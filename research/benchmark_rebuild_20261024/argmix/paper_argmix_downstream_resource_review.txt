ARGMix TRAIN0 downstream capacity review
24 October 2026. Source/config and prior sealed audit only; no tree/model/truth load, no launch.

Conclusion

The bridge's current Host RAM headroom wait is legitimate under the existing reservation policy. The saved admission review shows 1,332.7675 GiB MemAvailable against 1,379.5913 GiB required, a 46.8237 GiB deficit using active state PSS and live external AP PSS. Using all live PSS reduces the sampled deficit to 40.5066 GiB; both remain positive. Measurements are sequential, not atomic. The scheduler adds only each worker's cap minus observed PSS, so pages already reflected in MemAvailable are not simply counted twice. Session memberships do not overlap. The exact PID/start identity of external AP still matches; its unused growth allowance remains charged. The retired external American MLM PID is absent and contributes zero. Do not lower healthy-worker reservations or change the controller from this report. Completion of an admitted native ARGformer phase may naturally release enough unused growth reservation.

Predictable next-stage issue

Prior sealed native/clip audit: 52,032,035 nodes and 104,057,626 retained edge rows. No node or edge is dropped by the approved bridge. Mandatory node/edge payload is 3,538,023,724 bytes. Two int32 edge index arrays add 832,461,008 bytes, making 4,370,484,732 bytes before metadata offsets, sites/mutations, tree cursors, Python or output buffers. This exceeds the support task's 4,294,967,296-byte cap by 75,517,436 bytes. Thus the existing support cap cannot hold the required complete resident structures. This is a mathematical lower-bound finding, not a measured PSS prediction.

The proposed 32 GiB envelopes are conservative, unmeasured failstops. Only support is proved too small by the column/index lower bound. No claim is made that features/seal necessarily fail at 16 GiB, or that 32 GiB is a measured peak guarantee. Every stage still requires ordinary current admission. Calibrate from the first complete sanitized-tree consumer before making stronger guarantees for other parents.

support calls tskit.load on the sanitized tree and traverses native marginal intervals. It retains interval tuples selected by the fixed tree step, draws the original 100,000 support pairs with the unchanged CPython sampler/seed, and assembles TSV lines. One tree cursor can have arrays indexed by all global node IDs even though each active marginal tree is small. These resident structures and Python metadata are additional to the 4.370 GB lower bound. There is no full table dump/copy analogous to the bridge conversion. Output is approximately ten MB at this row count and retains the existing 32 MiB producer failstop. Do not change tree step, sample count or seed to fit memory.

features also calls tskit.load and holds one cursor, 100,000 target dictionaries, sorted row indices and memory-mapped output arrays. The source LCA binary-lifting table is explicitly limited to active nodes in the current tree; it does not allocate a 52-million-row lifting table. Nonetheless the underlying tree cursor/global time lookup and complete TreeSequence remain resident. At 100,000 rows and width 29, tokens/distances/nodes payload is 182,700,000 bytes plus three 128-byte NPY headers, comfortably below the unchanged 256 MiB producer bound. A chunk has at most 128 examples, 29 genealogy tokens and at most 3,222 donor candidates; pairwise token tensors have 128*29*29 entries. No all-parent pair tensor is built. Existing 14,400-second wall time is an unmeasured failstop; do not alter features or donor ranking to meet it.

treeloom_observation loads the same complete sanitized tree, verifies sites/samples/ages and support identities, and sums all marginal node occurrences. It writes a 100,000-row registry with four int64/float64 vectors (about 3.2 MB plus small NPZ metadata), within the unchanged 16 MiB producer bound. It does not build the expanded TreeLoom bank. It preserves limits max_nodes=1,500,000,000, max_holds=500,000 and 18*N+4*T <=32 GiB episode payload. N and T must come from the measured bridge/seal; the global native node count alone does not establish either quantity. Do not crop if a limit is exceeded.

Inert successor definitions and queue boundary

paper_argmix_tree_consumers_resource_successor_draft.json contains complete reviewed replacement definitions for all 42 support/features/seal tasks (14 parents), with TRAIN0's three task IDs identified separately. The only changed field is max_rss_bytes=32 GiB. Scientific argv, original config reference, source pins, output/auxiliary scopes, dependency graph, CPUs, wall times and output limits remain identical. All source hashes match and the candidate full DAG validates. These are proposals for the same task family, not evidence that future parent sizes are equal to TRAIN0.

All 42 tasks are currently pending at revision 5. Existing repairs._prepare permits only failed/blocked tasks, so the catalogue is deliberately not a repair-request/submission body and cannot be proactively dispatched through that API. No .ref.json, mutation helper or live-code change was created. ROOT must choose a separately reviewed queue-compatible application route; this report does not authorize modifying a running controller or manufacturing a task failure merely to make the API accept a repair.

Remaining capacity dependencies, separate from this three-stage draft

- The other 13 inferred bridges still have original 16 GiB RSS and 2 GiB producer limits. TRAIN0's measured dimensions establish its failure, not identical future parent sizes. They require an explicit family capacity policy or per-parent bounded header review before conversion; do not rediscover the same kind of undersized limit by intentionally failing every parent. The already reviewed generic capacity helper preserves the original scientific function, but broad application requires ROOT's scope/admission decision.
- Labels load segregated true ancestry, not the 52-million-node inferred tree. Their 4 GiB cap is not disproved by the inferred-tree audit. The original truth-table failstop is 8 GiB, so a future larger truth payload could exceed that cap; inspect generation receipt table bytes before labels rather than projecting native-inferred dimensions onto truth. No truth payload was read here.
- ARGMix model training/prediction use compact memory maps and selected batches, not whole native trees. Their 8/4 GiB host caps are not disproved by this audit. The fixed compact feature payload is about 183 MB per parent. Model maps include tokens and distances only: 171,100,000 bytes per parent, or 1,026,600,000 bytes for five TRAIN plus one VAL parts before labels, framework/runtime and batch storage. No change is recommended solely from this source accounting.
- Later TreeLoom fit/prediction load and expand the complete native bank, unpack all original genotypes, build episode/cut plans, and run the unchanged 32,325-parameter model with 512 GiB inner and outer RSS failstops. Source preparation still holds an explicit native-tree list while encoding. The 128 GiB optional single-parent cache and 32 GiB episode-payload cap do not bound total preparation RSS. A source/config-only proof of 512 GiB sufficiency is unavailable. Require the seal's N/T/S and complete bank/preparation accounting before starting fit; do not borrow American/AP dimensions or shorten the chromosome.
- Scratch release preserves every sanitized observed.trees for later TreeLoom. It releases only declared raw native scratch after features, labels and observation seal. The unchanged 40 GiB campaign scope therefore needs a running ledger of actual retained sanitized sizes and next-parent transient headroom. No blind 14-times-TRAIN0 projection is justified, and no cleanup is proposed here.

## Two explicit continuation modes

`exact_latest_boundary` requires genuine root terminal/cursor provenance establishing that the actual original optimizer count equals the chosen boundary and no completed parent update followed it. A checkpoint alone does not prove this. If that evidence is unavailable, this mode rejects the migration.

`root_authorized_durable_scheduled_checkpoint_rollback` requires a separate explicit active root rollback authorization. It uses the latest genuinely selected durable scheduled checkpoint and preserves that checkpoint's complete optimizer/cursor/RNG state. It does not require the latest live optimizer count to be observable. Later completed update count may remain null, meaning unknown. It discloses that later uncheckpointed work may be discarded and TRAIN work may repeat. It records the original attempt's elapsed wall time and provenance separately. It never claims that no work was lost or that physical work was only600 updates.

For example, a genuine boundary100 plus500 subsequent updates gives a scientifically effective600-update retained trajectory. If the old attempt completed unknown additional updates after100 and root explicitly rolls them back, those discarded updates are not silently counted as part of the retained trajectory. Their amount stays unknown unless actual evidence identifies it. Original elapsed time remains part of resource/runtime accounting. All original/failed artifacts are preserved. No fresh weights, optimizer reset, seed reset or None fallback is permitted in either mode.

Actual old terminal consumption, owned process drain, write/relaunch revocation and checkpoint/source provenance are mandatory in both modes. In rollback mode the no-after-boundary and exact-latest-counter assertions are not required. A negative or unknown old job exit can accompany a genuine complete scheduled checkpoint, but it is not reclassified as successful full training.

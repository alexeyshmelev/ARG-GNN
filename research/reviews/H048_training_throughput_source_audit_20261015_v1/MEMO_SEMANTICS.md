# Transaction memo semantics and narrower FLARE proposal

## Existing memo2 guarantee

`transaction_memo_adapter_v2.py` caches only within the original v4 mutex (143–156), with no cross-operation cache. Original `file_bytes` performs canonical path, type/link/size, O_NOFOLLOW, before/after identity and SHA checks on a miss (96–119). A raw hit returns the earlier bytes/SHA immediately (104–106). Canonical memo hits are restricted to the exact pinned original `file_bytes` and `reference` code objects (49–51,77–94), not arbitrary directory scans. Exit validates every cached canonical path and leaf identity uncached while still under the original mutex (122–150); cached entries are then cleared even on failure.

For a read-only consumer boundary, exit validation completes before its caller can perform its next write. It retains full journal enumeration, prefix replay, historical charges, current owned-scope measurement and source/authority comparisons. It does not reduce the number of guard boundaries, skip namespace/inode validation at exit, persist earlier snapshots across operations, or avoid acquisition of a busy mutex.

## Why not install this consumer adapter for reserve/close

Counterexample: within an operation, read a mutable authority/policy/metadata leaf A; it becomes B before a later read; a raw memo hit returns A, whereas original `file_bytes` would read B (or reject changed/missing/symlinked/multiply-linked data). Memo2 eventually rejects changed identity, but only on context exit. Current root reserve/close calls `_append` BEFORE context exit (prospective980 349–389). Therefore an event can be fsynced and its directory fsynced (333–345), then memo validation rejects without returning the mutation receipt. Post-commit failure/uncertainty is not equivalent to an earlier original rejection. A changed ancestor namespace has the same delayed-check problem.

The actual prospective980 mutation is append-only: old events are read at246–266; `_append` creates a previously absent numbered event O_EXCL, then reads it for the first time. Creation of this fresh leaf does not itself stale an old cached raw leaf, and direct directory canonical/list/stat operations are not memoized. Under strictly immutable old inputs, outputs could therefore agree. That restricted happy path does not establish original failure/commit semantics under identity change. Do not enable memo2 for root mutations. A future mutation-specific design would need explicit write-set exclusions/invalidation, unchanged fresh directory inventories and measurements, pre-commit validation before any durable side effect, defined post-commit uncertainty handling, and a separate policy/source review. No such implementation or policy change is proposed here.

Never cache parsed live state, directory listings, file stat results, nonexistence checks, process absence, owned-scope inventories, expiry, or PID identity across operations. Any changed/replaced/deleted/hard-linked leaf or changed namespace must reject before the affected next write. A memo cannot safely serve mutable writer output bytes after an in-operation rewrite without explicit invalidation. No new root guard operation was run for this review.

## Duplicate request-construction scans

H048 root driver83 reads full fresh state under one mutex, releases it, builds authority, then original `apply_reserve_v1`101 acquires a new mutex and rescans at prospective980351. FLARE driver208/230 does the same. Reusing the first state across that unlock would defeat exact-prefix rejection and is unsafe. Wrapping original `apply_reserve_v1` in an already-held independent flock can self-block; this is not a one-scan fix.

A narrower request-only improvement is possible only when root already has an authenticated genuine current-prefix receipt and complete pinned resource-binding roster: build the requested authority from those actual values outside the mutex, then let unchanged `apply_reserve_v1` perform its one fresh replay and reject any prefix/binding drift. No predicted tail hash, stale snapshot acceptance or automatic retry is allowed. If those actual inputs are unavailable, retain the preparatory inspection. A combined inspect/construct/apply API under one mutex would require a separately reviewed guard/API change; ordinary request construction alone cannot remove a necessary fresh-state validation.

Converter `american_c3_flare_convert_v1.py:107–108` invokes the full unchanged guard at site0 and every4096 sites. For the root-reported228,477-site VAL000 conversion, that is56 periodic checks, plus writer/stage boundaries. No source-only evidence quantifies time saved by memoizing those duplicated reads.

Current FLARE `root_stage_980_driver.py:46–52` uses the same original-only loader for admission and read-only worker/launch. Worker283 passes it into context, and context97 passes the same adapter into Writer. A fresh future successor may install the existing pinned consumer memo2 only after verifying/configuring the original guard in worker/launch fresh processes. Admission and close stay original/unwrapped. Bind memo2 and original v4 sources directly and transitively in the new admission closure, preserve all4096-site guard calls, writer checks, owned lifecycle, caps, expiry, CPU-only environment and immutable source pins. No live FLARE context, converter, author code or admission may be edited, resumed or replayed.

## Independent serialization reasoning

The original pickle Writer and the exact public CPython 3.11.17 Modules/_pickle.c were examined as source. The public C source independently matched SHA b8f6875c572368b62fcd2edeb7c094a77acd2aa58943d96e26b29485800d958f. The inspected C pickler uses 2/3/5-byte nonnegative integer opcodes, one-byte protocol 4+ MEMOIZE, 1000-item batches and bounded framing. The installed tskit Tree.parent and Tree.index source documents integer returns and calls the corresponding low-level integer-return APIs. Raw node IDs are nonnegative and below 106,769 for this exact tree.

Per dataset, 5*t+8*n+64*V+16MiB covers the unchanged raw int-list corpus and vocabulary. Each nonempty raw list contributes at most four structural bytes outside its integer payload. Outer-list batches add about two bytes per 1000 rows. The 8*n allowance and fixed margin cover these structures and framing, without assuming node integer memoization.

For the mapping, tuple overhead is at most three bytes per unique key, and set construction adds two bytes plus two per batch. The actual C save_set loop can emit an empty final MARK/ADDITEMS pair when a set has a multiple of 1000 elements. Including that behavior gives at most 7*P + 2*floor(O/1000) + 2*ceil(P/1000) + a fixed header allowance. Even using a 1024-byte fixed allowance before frames, this is 179,320,243 bytes, below 8*P=204,596,696. Thus the 8*P replacement does not silently omit those empty set batches. The retained 16MiB per-file mapping margin separately covers frame/fixed-header overhead.

Because the key begins with its sample, every sample/tree visit adds a distinct tree index to exactly one mapping set for that sample. The exact full mapping therefore has 1600 copies of every integer 0..76862 across sets. Their integer opcodes occupy at most 1600*(256*2 + (65536-256)*3 + (76863-65536)*5)=404,779,200 bytes. Set order cannot increase that term. The new mapping plan 5*T+8*P+404779200+16MiB preserves the ordinary tuple-to-set object.

The new NPZ helper uses the same direct np.savez_compressed on the same arrays and file stream, with unchanged Writer.prepare and finish. It does not create a scratch corpus or replace the format. Its schema checks exclude object arrays and bound member count, dimensions and dtype width. Its prospective budget is raw_nbytes+ceil(raw_nbytes/100)+1MiB per NPZ, a conservative allowance for the existing deflate output and fixed NPY/ZIP records. The installed NumPy _savez source was also read: it opens ZIP_DEFLATED members directly on the supplied stream, forces ZIP64, and calls format.write_array. The installed write_array source uses numeric/Unicode raw chunks on this path, with any buffering in memory. Those sources independently support the unchanged no-disk-scratch argument. There are seven such outputs. The six sidecars row payload is 920,717,352 bytes. Including the fixed original parent/class strings and the focal arrays gives 921,198,164 raw NPZ bytes. A sum-of-ceil upper bound plus seven 1MiB terms adds at most 17,032,832 bytes above the sidecar row term already in the aggregate. The six remaining 16MiB margins leave 83,630,464 bytes for the unchanged completion/directory/fixed auxiliary slack. Ten other 16MiB margins are retained in the ten pickle plans.

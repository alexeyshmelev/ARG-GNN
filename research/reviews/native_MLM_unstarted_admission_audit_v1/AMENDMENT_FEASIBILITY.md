# Proposed source amendment: conditional feasibility

A narrowly typed execution-only amendment is defensible within the repository's cooperative root-writer model, if root explicitly authorizes the exact exception and audits its implementation. It is a new execution contract over the existing fully charged allocation. It is not an existing API or a valid unchanged-v4 relaunch.

The original reservation, storage, 41 source bindings, policies, prefixes, journals, failed logs and v4 sources remain immutable. All 15,032,385,536 bytes stay charged. Original output and both auxiliary roots stay the same. Actual v5 producer/launcher/context/helper hashes come from a separate exact amendment authority. They must never be inserted into a copied original reservation or presented as v4.

Minimum execution changes are:

1. A one-key, one-attempt amendment validator binding the original allocation and failure evidence, actual new transitive source closure, exact input/caps/config/runtime/corpus and explicit old-launch revocation.
2. A versioned root driver/contract that uses a fresh attempt subdirectory inside original auxiliary scope, preserves the original output/tmp roots, and writes honest v5 provenance. No admit or reserve call.
3. A versioned GPU launcher source check. The original launcher's lines 112–115 require the actual module in original consumer_bindings, so it rejects v5. The new gate must validate actual v5 membership from the amendment and original allocation separately, preserving original lease, GPU4 UUID, memory reservations, sharing/title/input/runtime and real wait behavior.
4. New consumer/context source checks. The current contract at 85–117 and context at 21–33 and 124–140 bind v4 paths/driver/input/source hashes. New versions validate actual amended lineage, then call the unchanged v3 allocation/boundary checker with the exact original storage object. Do not call the old validate_storage API with new refs or claim it validates them.
5. A local pidfd backend used by both supervisors. A reviewed syscall backend may solve absent Python/libc convenience symbols on the recorded x86_64 platform, but kernel support is unverified. Keep identity-before/open/identity-after and fd-only signaling. No global monkeypatch or numeric signaling fallback. Fail closed before launch side effects.
6. A root completion lineage adapter. The original close driver pins v4 receipts. A new evidence adapter can validate genuine v5 launch/wait/completion and amendment lineage, then use unchanged v3 close_completed on the original reservation and scopes. Credit is possible only after real completion/direct wait0, full old/new writer revocation and root absence evidence.

All new attempt sources, authorities, metadata and logs must fit the originally charged scopes or existing authorized metadata allowance. A scoped exact script entry may be needed if the new source lives under original worker_aux rather than src/arggnn. Preserve science, BERT configuration, full TRAIN000 corpus, seed, 512-token qualification, GPU4/UUID, native interpreter/packages, lease/title/input checks, exact resource limits and the original absolute expiry of 2026-10-16T10:01:33.907094+00:00. No renewal or deadline reset.

Root must serialize one-use activation under the original scheduler mutex, check original output/tmp freshness, bind the actual old outer exit1 evidence without inventing a scientific-worker wait, prove all old writers absent, and revoke every old launch/resume/write capability. The new attempt needs lifetime exclusion, explicit active-attempt checks at every supported launch/write boundary and no automatic replay after another failure. Retain every failure and partial artifact.

Revocation has a material limit: a new authority file cannot make frozen old code read an amendment predicate. Existing v3 checks whether the allocation is open. If rigorous enforcement means every historical direct entrypoint must mechanically reject while its bytes remain unchanged and the allocation stays open, that requirement is unsatisfied. Conditional feasibility relies on explicit cooperative root-capability revocation, as used by this repository, and does not claim hostile-process enforcement.

No accounting API change is needed in this design. No amendment implementation, policy activation, guard import/call, accounting read/mutation, scope inventory, process action or GPU action was performed. Source-only evidence and exact touchpoints are in amendment_feasibility.json. Root decides whether to authorize and implement the new execution contract.

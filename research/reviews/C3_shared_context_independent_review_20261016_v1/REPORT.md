## Cost, RAM and storage limits

The source reduction is credible:2B authenticated block gets instead of6B; B value encodes plus B gradient re-encodes instead of4B encoder entries; B encoder backward graphs instead of2B. Both directional GRUs and the classifier retain their original checkpointed work. The stated3Q versus6Q site-call accounting is a source/replay count with checkpoint early-stop caveats, not measured kernel work or speedup. The packet makes that distinction.

The new tradeoff is persistent within-step CPU context storage: `V=T*1600*32*4` bytes for values, another `V` for leaf gradients, plus transient/metadata/boundary/focal allowances. The forecast's4V+2M cap is prospective planning, not an actual PyTorch allocation/RSS certificate. The per-bank byte expression is consistent with original tensors: at most100bytes/node,8bytes/tree/sample, H+130bytes/site for int8 genotypes and up to four alleles/six donor channels, plus tree/sample/focal metadata. This covers one cloned feature bank, while existing cached/source state and autograd/kernel work remain outside that category.

No complete total CPU/GPU/durable-storage fit or wall-time saving follows from these formulas. Actual root caps and existing whole-process guards remain necessary. Contexts/adjoints are discarded within the update and are not returned for checkpointing or reused across updates. The original model/optimizer snapshots and six-candidate schedule remain; added counters/forecast fields also enlarge serialized history metadata, so no disk-budget saving should be inferred.

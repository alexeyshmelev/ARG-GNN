# H058 and C3 source-derived learning-efficiency map

This is a static diagnosis of the exact admitted sources. No live stack, timer, utilization probe, dataset payload, truth, guard import or execution was used. It does not establish what either current worker is doing or the cause of a sampled idle GPU.

## H058: substantial work before the first update

The admitted run is the original 32 TRAIN parents, each 2 Mb with 952 haplotypes and 686 queries, 30 passes and two arms. It schedules 960 full-parent updates per arm, 1,920 total. The metadata totals are 30,531 marginal holds, 58,100,493 native vertices and 426,936 SNPs across the 32 parents.

- `observations_v1.load_observations_v1:59-129` retains all32 banks, builds all32 episode arrays and all64 parent/arm packed payloads before returning to the training loop. Two original CPU spawn workers decode parent banks, but episode/null/packed construction is serial in the main caller. The first optimizer update therefore follows the entire phase-wide observed preparation barrier and the original TRAIN target-mass preparation. This is source ordering, not an observed current phase.
- `build_clade_episode_arrays_v1:90-126` performs CPU forest/clade traversal and dictionary membership across adjacent trees. `prepare_packed_parent_v2:189-267` makes a full Python parent list, three global vertex passes, per-hold DFS, local maps, height/rank/CSR construction and 15 tensor buffers per hold. Both arms independently repeat this mostly identical topology work. The metadata forecasts 457,997 tensor objects per arm, 915,994 total, and 4,583,313,720 packed numeric bytes for both arms.
- These routes and episodes are actually cached. `FrozenEpisodeCacheV1` replaces repeated full-bank hashes with active identity/version checks after sealing. `FrozenPackedCacheV1` does not rebuild a route per update. A diagnosis that blames per-step route rebuilding is incorrect.
- Each parent residency transfers the full bank, episode and target once, synchronizes, then executes both arms before release (`observations_gpu_v1:13-35`, producer `run_train_v1:288-308`). Nevertheless `payload_v1:38-53` invokes the original full current-observation binder independently per arm. `compare_original_bank_v2:51-61` and `compare_observation_tensor_chunks:37-48` copy every device bank field back to CPU in <=1,048,576-element chunks for comparison, then similarly compare episode fields. That is 1,920 complete bank/episode comparison traversals over the full budget. Static metadata bank-dtype bounds imply about391.45-562.15GB of bank D2H comparison traffic across training, plus episode traffic. These are aggregate logical byte bounds, not measured PCIe traffic or timings.
- The model is PyG at forest levels, but its same-marker adapter is called in a Python loop for every hold (`integration_hooks_v3:65-75`) with nested whole-hold and16-marker checkpoints (`same_marker_packed_csr_v2:411-439,476-500`). This schedules 1,831,860 forward hold calls over both arms and30 passes before recomputation. Backward stage/hold/block recomputation is deliberate to fit memory and has no measured cost split here.
- The two first genuine steps use full guards. Later steps retain the reviewed math-effect gate, active resource/lease/census checks and pre/post cache validation. Startup/read/write/residency transitions still use full guards. No new guard weakening or parser successor is recommended.

## C3 VAL000: serial full input reconstruction twice per checkpoint

The admitted pending set is only epoch30. Its immutable plan has30,000,000bp,1,600 haplotypes,10,000 focal records,76,527 trees,202,122,280 marginal vertices,228,477 SNPs and2,392 blocks. Block limits remain32trees/250,000vertices/4,096sites. Actual immutable plan maxima are86,354 vertices and192 sites per block. None of these supports is reduced.

- The current caller explicitly selects `num_workers=0,pin_memory=False` (`worker_v1:131-132`) despite Dataset support for spawned workers. Thus `__getitem__`, all CPU features, model transfer and GPU inference run sequentially. No CPU prefetch or pinned transfer overlaps those stages.
- Each direction has a new Dataset state. `load_observation:28-92` authenticates/loads the full observed tree sequence, genotype axes, allele rows and focal joins once per dataset. Each block then reconstructs every native tree (`native_tree:48-54`) and encodes all whole-tree features (`encode_block:75-129`). It processes202,122,280 vertices and228,477 sites per direction. The reverse pass repeats the same direction-independent CPU features and GNN tree encoding. The full pending cell entails4,784 block feature builds,153,054 tree conversions and404,244,560 marginal-vertex enumerations.
- Within each non-isolated tree, `encode_block:94-107` calls `_layout_with_isolated_samples`, then `branch_concordance_support_v1:271` calls `_layout` again. Layout is repeated twice per tree, not once per SNP. The costly per-SNP component is `branch_concordance_support_v1:280-305`: each nondegenerate SNP allocates descendant allele counts and runs a Python postorder accumulation across every vertex. Its work is O(sum_t informative_sites_t * vertices_t), in addition to repeated full layout traversal. No per-tree site distribution or informative-site count was opened, so no precise traversal count or runtime share is claimed.
- `streamed_focal_predictions:17-79` runs in inference mode. Both recurrent scans correctly preserve state over all blocks and only reset at chromosome endpoints. Sparse10,000 focal scoring does not permit skipping nonfocal trees because they alter recurrence.
- `GuardedLoaderV1:151-156` calls the fast check before and after every block, at least9,568 block checks for this cell. After STATE initialization, `active_amendment_v1:265-271` rereads the1,930B input and4,585B request and rehashes the93,258B manifest. It does not reauthenticate all469 manifest source entries at each block. `manifest_v1:53-56` traverses those5executed+464authentication refs on full request validation. Full accounting remains at writer boundaries. Do not conflate fast checks, initial admissions and full accounting.

## Highest-impact feasible future change

Replace repeated CPU feature construction with one bounded immutable block-feature preparation/cache component, then reuse the identical encoded observation bank for opposite scan directions and pending checkpoints. Within each tree, derive layout/postorder once by exact source identity and batch SNP allele-count propagation through that postorder rather than dispatching a Python vertex loop per SNP. Preserve the same allele-split, tie, unary-branch, missing-call, site/sample order and feature definitions. Keep donor labels, query masks and support unchanged. Reuse only CPU observation features, never learned tree embeddings across different checkpoints.

A direction-independent block is identical in both scan directions because geometry uses global neighbor spans and chronological block contents. Existing recurrence can consume that same bank in opposite block order. A bounded cache must charge its actual bytes, reject drift, and either hold a reviewed bounded subset or use a separately admitted immutable feature artifact. No new cache, spill, DataLoader workers or storage writes are authorized in the current live32MiB C3 allocation. Synthetic FP32 tensor equivalence can establish local semantics, but full-parent fit, speed and source-lineage integration remain unproved. No live adoption, v6 bridge or restart is proposed in this diagnosis.

## Prior observations versus static evidence

The earlier FLARE lock report records ROOT-observed scheduler ownership handoffs between FLARE and C3. Those observations show lock churn rather than a proved permanent deadlock. The consumer already caches raw bytes and narrow canonical calls inside each original mutex transaction. Parsing and predicates still execute, and final uncached namespace/leaf validation remains. ROOT's earlier13GB/500klogical-read admission observation is historical and is not a current stack, physical read count or causal timing breakdown. This new report adds source-derived multiplicities only.

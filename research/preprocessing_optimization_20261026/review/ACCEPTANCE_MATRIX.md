## Scope and method boundary

The reference for exactness is the currently admitted implementation and its pinned inputs. Its existing optimized observation encoder explicitly says `historical_support_byte_identity_claimed=False`; equality with the current route must not be represented as equality with every older implementation.

| Proposed change | Acceptance decision | Required proof |
|---|---|---|
| Faster VCF decoding in our external observation adapter | Eligible | Every retained genotype, allele count, coordinate, sample identity, reference class, age, and source reference identical; same input rejection contract. |
| Compiled integer forest bookkeeping in our TreeLoom preprocessing | Eligible | Byte-identical arrays, dtype, ordering, representative selection, metadata counts, and downstream cut/episode arrays. |
| Independent parent preparation or native-tree extraction ahead of execution | Eligible with bounded admission | Main consumer keeps exact parent/window order; per-worker state private; global ordered merge; no RNG consumption or model execution in producer. |
| Shared compact observation cache | Eligible with provenance and resource proof | Key binds exact input hashes, parser/encoder source, schema, protocol, sample order and all preparation parameters; immutable payload and exact expansion; cold-build and cache costs reported. |
| Author GST, ARGformer, FLARE, AP model/training behavior, including runtime monkeypatches | Outside this optimization scope | Do not alter architecture, forward, loss, optimizer, batch/microbatch, mask, dropout, sampling, precision, recurrent state, or training budget. Unchanged files alone do not prove unchanged runtime behavior. |
| Our external inputs to an author method | Eligible only at the input boundary | Byte-identical actual model-facing tensors and row order, including all native trees/sites and no-focal windows; original model/loader/RNG schedule preserved. |
| Raising worker count or changing prefetch on an author training loader | Defer | It can change stochastic assignment, main RNG draws, memory, and timing. It is not implied by approval to accelerate our VCF adapter. Leave current active GST and ARGformer untouched. |
| New GPU arithmetic partition, mixed precision, TF32, changed reductions or skipped checks | Not accepted as preprocessing | Separate numerical review required; not an interchangeable CPU plumbing change. |

## Concrete findings from active source

1. AP TreeLoom prediction and GST share `european_treeloom.load_relate_observation` (lines 95-210). The parser validates every data row's width/position before checking whether that position is retained. A retained-only compiled reader must not skip those global guards. Parsing itself is integer work and can be made exact without touching an author model.
2. GST `dataset.load_parents` prepares every parent in plan order before its DataLoader exists. Its four persistent spawn workers therefore cannot speed up initial parsing. The current repair dataset uses one advancing tskit cursor per worker; a replacement must preserve eight consecutive complete-tree windows and reset safely on parent changes or reverse accesses. Spawn serializes states, so multiplying loader workers can duplicate large parent arrays.
3. GST training processes no-focal windows with a no-grad forward deliberately to retain dropout draws. Full-parent loss is summed over focal windows, divided by the parent's focal count, and stepped once per parent. Its resume creates the DataLoader iterator before restoring saved main RNG to undo the extra worker-base-seed draw. Preserve that exact ordering. Parent order is `Random(20261024 + epoch).shuffle(plan.train_parent_ids)`; the full budget is 90 updates.
4. American TreeLoom uses one `ThreadPoolExecutor` producer, one parent lookahead and a lossless compact all-20 RAM cache. This is real overlap, but CPU Python loops remain GIL-bound. Its `MemoryGovernor` reserves concurrent phases using main-process current RSS; a new process pool needs explicit aggregate admission, not just the existing periodic PSS enforcement.
5. American TreeLoom epoch order is `Random(70002 + epoch).shuffle(registry.ids('train'))`. The current run resumed at update 238, and its consumer checks the exact next schedule element. The resumed numerical task still executes through final update 600, with 49 AdamW states and 32,132 parameters. CPU preparation must not touch RNG, optimizer, recurrent execution, or checkpoint cadence.
6. Native clade extraction can be parallel per tree, but the following merge is sequential in native-tree order. `previous`, `previous_episode`, dict insertion order and FP32 spans are observable semantics. Arbitrary-width masks at 1,600 samples do not fit a single uint64; collision-prone fingerprints are insufficient.
7. The American static preparation facade imports the CURRENT `research/repairs/benchmark_recovery_20261020/runtime/{observations,episodes,cuts}.py` route. That route already uses vectorized stable levels, forest ownership, cut grouping, bounded fingerprints and pair layouts from `indices_v1.py`; benchmark against it, not an older Python-loop route. AP uses the older compatibility route, whose connected holds dispatch to original connected implementations. Patching only one alias can miss a production branch.
8. The existing encoder supports only all-sampled/all-isolated zero-SNP forests, with no virtual root. Mixed forests are rejected. A fast implementation must preserve that restricted behavior and the empty support encoding (all zeros except empty=1).
9. The current AP executor repeatedly transfers blocks and intermediate `up`, `out`, forcing and leaf context between CPU and GPU. That is a future profiling target, not evidence that increasing CPU parallelism alone will saturate the GPU. Altering arithmetic partitions is outside this exact-input patch.
10. ARGformer already has eight workers, persistent loaders and prefetch=2. Its wrapper authenticates native dataset/order/vocabulary/focal references before import and preserves author epochs. Contrastive microbatch=4096 is explicitly required because splitting it changes in-batch negatives. Do not tune these author behaviors under an input-plumbing optimization.

## Execution route and rollout

The audit used `/usr/bin/ssh anogena` directly; effective SSH configuration selected the authorized host/account and no proxy command or jump wrapper. Only readable `sed`, `cat` and literal Python source were dispatched. No private key or credential contents were read. The active campaign path inspected is scheduler -> visible Python `-B -s -m arggnn.benchmarking.paper_campaign.runtime --task <json>` -> source-authenticated factory/function. No encoded executable payload is involved in that path.

`repairs.apply_pending` means pending repair submissions, not pending tasks. `_prepare` accepts only actual FAILED or BLOCKED rows, exact expected attempt and plan revision, the same resource kind/output/auxiliary scopes, and an absent old output directory. It rejects healthy pending/running tasks. The controller holds its plan in memory; changing the on-disk plan cannot update its current tasks safely. Do not manufacture a blocked status or mutate source pins to force admission.

An explicitly authorized operator cancellation of only our TreeLoom worker can use the existing route after a real failure is recorded, with all of these conditions:

- Demonstrate net benefit after lost in-flight work, all cold compact-cache rebuilds, process/JIT startup and resource competition. A warm complete cache can make retaining the existing worker faster even if isolated cold preparation improves substantially.
- Identify the owned process by PID and start identity; preserve author workers and controller. Let the scheduler obtain the actual exit/wait and drain evidence before issuing a repair. A progress label is not a durable checkpoint.
- Capture the stable checkpoint only after exit/drain, or use an independently proven race-safe immutable capture. `latest.pt` is atomically replaced before `latest_checkpoint.json`; the metadata can lag after interruption. Authenticate and inspect the checkpoint itself. Never treat an unfinished `.next` file as committed state.
- Validate all 49 FP32 model/AdamW states, nonnegative finite second moments, every step counter equal to the saved complete update, unchanged settings/contract/registry, schedule identity, `last_completed_parent`, `next_schedule_index`, and Python/NumPy/Torch CPU/CUDA RNG. Restore after model/optimizer/device setup and before any numerical work. Prefetch must not consume those generators.
- Preserve the original all-20 observation barrier and every referenced plan/focal/input hash. Preserve old attempts, logs and files in an accounted immutable archive. Review path dependencies before any archive move: a source-bound reference is path plus hash, so moving its file can break resume even when bytes survive.
- The current outer wrapper hardcodes update238 and its output leaf. A replacement must explicitly bind the newly captured boundary and a fresh leaf, preserve the expected final completion product location, and handle the repair rule that the old top-level output scope must be absent. Do not reuse the update238 assertion for a later checkpoint.
- Submit complete replacements with original pins plus candidate pins/receipt, exact expected revision and attempt, actual archive byte accounting, and stable copied checkpoint/evidence references. Source and cache changes must not overwrite historical evidence.
- A downstream task becomes repairable only if the scheduler actually records it blocked/failed. Pending successors remain ineligible. Let a warm prediction finish if replacing it would discard more work than the candidate can recover.

GST checkpoint validation additionally requires exact source-list equality. Adding source refs silently to a resumed checkpoint is not compatible with that validator; any future migration would need explicit provenance handling. Current rollout should leave active GST and ARGformer intact as proposed.

## Opportunities after the first patch

Measure before changing: compact-cache pack/hash/restore and integer-index reconstruction on every TreeLoom parent visit; repeated authentication I/O and large JSON site-join materialization; multiple full observation copies at spawn/pin-memory boundaries; CPU/GPU transfer and synchronization time; stage reservations that hold a GPU during long CPU preparation; and scheduler storage/RAM waits. Existing safety checks, source authentication and training semantics remain requirements. Safe improvements can include bounded immutable shared arrays, a bounded authenticated compact-input cache, ordered next-parent preparation and separate reported CPU preparation stages. Each needs its own exactness, resource and total-runtime evidence.
